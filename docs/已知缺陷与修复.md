# Wayfare · 已发现的真实缺陷与修复

> 本文件是 P7-A 验收第 4 项的产出：**「已发现的真实缺陷及修复」**。
> 收录的是项目推进过程中由**测试或真实联调**抓出来的真问题，不是「可能会有的风险」。
> 每条都写清：症状 → 根因 → 怎么发现的 → 修法与代价。
>
> 这份清单比「测试全绿」更能说明工程质量：**能被自己抓出来的 bug，才有资格说测试有用**。

---

## 1. `/api/api/...` —— 路径写了两遍，接口返回 500 而且看着像「静态资源找不到」

- **症状**：`POST /api/trip/plan/sync` 返回 HTTP 500，日志是 `NoResourceFoundException: No static resource ...`。
  报错说的是「找不到静态资源」，完全指不到「路径重复」这个真实原因。
- **根因**：`server.servlet.context-path` 已经是 `/api`，Controller 上又写了 `@RequestMapping("/api/trip")`，
  真实路径变成 `/api/api/trip/...`。
- **怎么发现的**：P3-F 的真实联调（手工 curl），编译与单测都发现不了 —— 单测不走 servlet 容器。
- **修法**：Controller 只写应用内路径。已写进 `MEMORY.md` 的常驻约束：**新增接口照抄 `/works` `/profile` 这种写法**。
- **代价**：一次联调往返。

## 2. `enrichRoutes` 边回填边判断 → 整天的点位挂了 `VERIFIED` 却没有任何距离

- **症状**：地图开着生成出来的行程，每个点位都标着 `VERIFIED / BAIDU`，
  但 `distanceMeters` 全是空 —— **标记在骗人**。
- **根因**：坐标与 poiUid 是 Step 6 从候选池回填的（P3-D 的 draft 不带坐标）。
  代码先逐段判断 `hasCoords(next)` 再回填，于是判断时 `next` 还没坐标 → 每段都被判「无坐标」→ 全天走 `setNoRoute`。
- **怎么发现的**：P3-F 真实联调，检查响应里的距离字段。
- **修法**：改成**先整天回填事实 → 再决定分段**（两阶段）。已写进 `RULES-PIPELINE.md`。
- **代价**：一次联调往返；若没查距离字段，这个 bug 会一路活到答辩现场。

## 3. 阶段日志的 `trip_id` 全是 NULL → 「按行程拆解 token 与成本」严重漏算

- **症状**：`GET /admin/generation/trips/{id}/breakdown` 只统计得到 COPY 一段的 token，
  而这次生成实际烧了约 13000 tokens（差一个数量级）。
- **根因**：`PARSE` / `CANDIDATE` / `COMPOSE` / `VALIDATE` 四处 `new AiStageRecord(...)` 把 tripId **写死成 null**，
  其中一处的注释还写着「解析阶段还没有 tripId」—— **那句注释是错的**：`orchestrate` 在 Step 1 之前就已经
  `createDraft` 拿到了 tripId。
- **怎么发现的**：两次真实地图运行后核对日志表（`external_call_log` 显示 9 次 LLM 调用，拆解表却只有 1 段）。
- **修法**：新增 `TripRunContext`（ThreadLocal 承载本次运行的 tripId），`orchestrate`/`replan` 里 set + finally clear，
  四处改为读上下文。**不改方法签名**，因此 74 个既有单测零改动通过。
- **代价**：一次真实运行 + 一次表核对。这个数字要上简历，所以漏算比报错更危险。

## 4. qwen 在调用日志里被记成 `OTHER`

- **症状**：`external_call_log` 里 qwen 的 `connector` 是 `OTHER`，而不是 `LLM`。
- **根因**：`GovernedExternalHttpClient.inferConnector` 的域名推断表只认 `bigmodel.cn` / `deepseek.com`，
  没有 `dashscope.aliyuncs.com`。
- **怎么发现的**：P4-C 的成本统计核对（按 connector 分组时发现 LLM 那一行少了一大截）。
- **修法**：补 `dashscope.aliyuncs.com` 与 `moonshot.cn`。
  **连带教训**：加新厂商必须同步补这张表，否则 P6 诊断与 P7 指标会静默漏掉它。

## 5. 大模型没接熔断 → 坏掉的厂商被反复选中，每次白等 90 秒

- **症状**：两次真实运行合计**白等约 9 分钟**；qwen 的失败模式是「长输出跑满 `llm.timeout-ms`(90s) 才判超时」，
  而且下一次请求还会再选它。
- **根因**：`CircuitBreaker` 只接在**地图**连接器上。`LlmCapabilityResolver` 的类注释里明明写着
  「P1-D 会在 isAvailable 里补上熔断」，**这个 TODO 一直没做**。
- **怎么发现的**：P3-F 联调时统计 `external_call_log`：9 次 qwen 调用 6 次失败，`max=90014ms`。
- **修法**：`recordFailure(name, configPrefix)` 按前缀取阈值（**llm=3 / map=5**，因为大模型一次失败损失一整段 90 秒，
  地图只损失几百毫秒）；`isAvailable` 加熔断判断；流式路径（绕过 `execute`）单独补 `recordProviderFailure/Success`。
  另加 6 条单测钉住机制。
- **残留**：第一次超时仍要等满 90 秒 —— 这是阈值机制的本质，不是 bug。

## 6. 熔断快照写死读 `map.breaker.*` → 大模型被显示成「阈值 5」，实际第 3 次就跳闸

- **症状**：管理页上大模型卡片显示「熔断计数 0/5」，但它实际第 3 次失败就打开了 —— **界面与事实矛盾**。
- **根因**：`CircuitBreaker.state(name)` 把 `map.breaker.*` 写死在快照里，而阈值是按前缀读的。
- **怎么发现的**：P6-A 做完接口后用 curl 冒烟，看到 `breakerThreshold: 5` 与代码里的 llm=3 不符。
- **修法**：加带前缀的重载 `state(name, configPrefix)`，单参版本保留并委托给 `"map"`（既有调用方零改动）；
  抽出 `defaultThreshold(prefix)` 让写入与快照共用同一份默认值。加 1 条测试锁住。
- **为什么值得单列**：**诊断信息说谎比没有信息更坏** —— 没有信息时人会去查，信息错了会让人查错方向。

## 7. 离线 Mock 的三个阶段返回同一份 JSON → 「没有 Key 也能跑通全链路」当时不成立

- **症状**：关掉地图、把 provider 切成内置 `mock`（这正是「一台干净机器 clone 下来也能演示」的路径）后：
  `{"shortage":true, "shortageHint":"没有检索到任何可用的点位", "composeError":"候选池为空"}` —— 出不了行程。
- **根因**（两个叠在一起）：
  1. `MockLlmProvider.chatJson()` **对三个阶段一律返回意图 JSON**，而候选检索要的是 `{"candidates":[...]}`；
  2. 三类 JSON 的**字段名是按手册文字臆想出来的**（`themes` / `constraints` / `items[].name`），
     与真实 DTO（`preferenceTags` / `ItemDraft.poiRef`）对不上，反序列化时被静默忽略。
     Mock 自己的 javadoc 就预警过这件事，但一直没回来对齐。
- **怎么发现的**：P7-A 新增的离线全链路集成测试（`TripOfflinePipelineIntegrationTest`），
  断言「离线也必须产出行程条目」直接失败，并把完整响应打进了断言消息。
- **修法**：`chatJson` 改为**按调用方给的 `jsonSchemaHint` 路由**（候选阶段含 `candidates`、
  编排阶段含 `poiRef`），而不是猜 prompt 关键词 —— 候选阶段的 prompt 里恰好写着「行程天数」，
  按关键词判断会走错分支（这个坑上一版就踩过）。三类 JSON 全部按真实 DTO 字段名重写，
  并让候选名称与编排里的 `poiRef` 一致（否则 P3-E 的 CLOSURE 会把它们全判成池外）。
- **顺带补上的守卫**：那条集成测试现在守着整条离线链路，改任何一类 JSON 都必须跑它。
- **代价**：一次测试往返 + 一次修复；换来的是 README 里那句承诺**变成了真的**。

## 8. 「改别人的行程顺序」原本不需要是本人

- **症状**：`updateItemOrder` 的实现里只比对 `tripId`，没有校验 userId。
- **根因**：P2-B 预留了实现但没有 Controller 入口，因此绕过归属校验这件事一直没被发现。
- **怎么发现的**：P5-B 要加排序接口，读实现时发现签名里没有 `userId`。
- **修法**：签名补成 `(tripId, userId, dayIndex, itemIds)` 并校验归属；新增 `PUT /trip/{id}/days/{dayIndex}/order`。
- **同类**：`/trip/{id}` 原先「不存在」与「不是你的」都返回 404，等于把越权访问伪装成资源不存在 →
  已区分为 404 / 403（**代价是 id 可被枚举探测**，权衡已写进方法注释）。

## 9. 公开路径白名单是「完整匹配」→ 公开的攻略详情页拿不到行程

- **症状**：未登录浏览攻略详情页时，行程区块不显示。
- **根因**：`JwtInterceptor.PUBLIC_PATHS` 里已有 `/works/{id:[0-9]+}`，但 PathPattern 是**完整匹配**，
  它匹配不到带后缀的 `/works/{id}/trip` → 未登录请求被 401。
- **怎么发现的**：P5-C 联调时用未登录请求打过这条接口。
- **修法**：白名单单独加一条。已写进常驻约束：**新增带后缀的公开路径必须单独登记**。

## 这些缺陷的共同点（值得写进答辩）

1. **单测发现不了它们**：9 条里有 7 条是在**真实联调 / 真实数据核对**中抓到的。
   单测证明「我的代码按我理解的方式工作」，证明不了「它按现实的方式工作」。
2. **最危险的不是报错，是静默**：`/api/api` 报了个指向错误方向的 500；
   而 `trip_id=NULL`、`OTHER` 归类、Mock 字段名丢失都是**完全不报错**的 —— 数值小了一个数量级、
   字段静默变 null。所以「用真实数据核对统计口径」是这套代码里性价比最高的一道防线。
3. **注释会骗人**：「解析阶段还没有 tripId」这句注释与代码事实相反，直接导致了缺陷 3。
   现在凡是「为什么这么写」的关键判断，注释里都带上依据。
