### 2.2 分组视角（把「整体一定很低」这件事说清楚，而不是藏起来）

| 范围 | 行覆盖 | 分支覆盖 |
|---|---|---|
| 全库（所有类） | 51.4% | 41.0% |
| **`trip` 包（AI 编排管线，本项目核心）** | **86.2%** | 66.6% |
| `connector` 包（连接器与治理） | 42.7% | 25.1% |
| `service` 包 | 22.7% | 16.0% |

**为什么全库只有 51.4%**（如实说明，不修饰）：
1. `service` 包 2291 行里绝大多数是**从「光影集」迁移过来的内容域/社交域 CRUD**（作品、评论、私信、点赞、关注…），
   属于 P0 的既有代码，**不在 P7-A 的测试清单里**（手册 P7-A 点名的类是 PreOrderService / TripValidator /
   IntentSchemaValidator / BudgetCalculator / MaskUtil / ProfileRenderer + 八类集成场景）；
2. `connector` 包的偏低主要来自**真实厂商的 HTTP 实现**（glm / deepseek / qwen 的请求构造），
   覆盖它们需要真实 Key 或 HTTP 打桩，而这部分的风险已由「出站治理 + 熔断 + 脱敏」三条链路的测试覆盖住；
3. `TripStreamService`（SSE，287 行）几乎未覆盖 —— 见第四节「未覆盖与原因」。

> 口径说明：手册写的是「**重点类**覆盖率报告，目标 > 60%」，按这个口径全部重点类都达标（最低 76.6%）。
> 全库 51.4% 也一并给出，因为「只报达标口径」不是诚实的做法。

## 四、未覆盖项与原因（不含糊其辞）

| 未覆盖 | 原因 | 谁来覆盖 |
|---|---|---|
| 场景 1：地图可用 → `VERIFIED` | 需要真实百度地图 AK 与网络；用桩件伪造 `VERIFIED` 等于**没有验证真实链路** | `-Dwayfare.live=true` 的 LiveTest（真实 AK） |
| 场景 6：大模型超时 → SSE error | 需要真实超时（≥90 秒）或对 `LlmProvider` 做深度打桩；后者测不出真实的超时行为 | 手工联调（已实测：qwen 90s 超时后降级 glm） |
| `TripStreamService`（SSE，287 行） | MockMvc 对 `text/event-stream` 的异步流支持有限，且它依赖线程池与登录身份重建；写出来的「绿」证明不了真实断线行为 | 手工联调（已实测：断开后 104 秒内检测到并掐流） |
| 真实厂商 HTTP 实现（glm/deepseek/qwen 请求构造） | 需要真实 Key；风险已由「出站治理 / 重试 / 熔断 / 脱敏」的测试覆盖 | LiveTest + 真实联调 |
| 内容域/社交域 CRUD（`service` 包的大头） | 属 P0 既有代码，**不在 P7-A 的清单内** | 未安排（如需提升全库覆盖率，这是唯一的大头） |
| 前端（Vue） | 本项目未引入前端测试框架（手册也未要求） | 页面目视验收 + 构建校验 |
