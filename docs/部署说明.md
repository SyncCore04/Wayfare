## 1. 十分钟概念速成（不懂这 7 个词，后面全是天书）

| 词 | 一句话解释 | 类比 |
|---|---|---|
| **镜像 image** | 一个打包好的「只读模板」：里面是一套文件系统 + 启动命令 | 装系统的 ISO / 一份菜谱 |
| **容器 container** | 镜像跑起来的一个实例，可读可写、用完可丢 | 按菜谱做出来的一盘菜 |
| **Dockerfile** | 描述「怎么把镜像做出来」的文本文件，一行一条指令 | 菜谱本身 |
| **多阶段构建** | 一个 Dockerfile 里写多个 `FROM`，前面阶段负责「编译」，后面阶段只拿编译产物 | 厨房做菜 → 只把菜端上桌，不把灶台一起端上来 |
| **volume（数据卷）** | 一块**独立于容器生命周期**的存储，容器删了数据还在 | 硬盘 vs 内存 |
| **compose 网络** | compose 会给所有服务建一个虚拟网络，**服务名就是域名** | 同一个局域网里用主机名互访 |
| **docker compose** | 用一个 YAML 一次定义并启动多个容器 | 一键启动整套系统的脚本 |

### 🔴 最重要的一条心智模型

```
容器里的 localhost ≠ 你 Windows 的 localhost ≠ 别的容器
容器之间互相访问，用「服务名」当域名
```

- 后端容器要连数据库，**不能写 `localhost:3306`** —— 那是指「后端容器自己内部的 3306」，那里没有 MySQL。
  要写 **`mysql:3306`**（`mysql` 是你在 compose 里给服务起的名字）。
- 你在 Windows 浏览器里访问前端，走的是 **端口映射**（`宿主机端口:容器端口`）。
- 这三者混起来，是初学者 80% 的报错来源。

### WSL2 是什么，Docker 为什么在它里面跑

Windows 上跑 Linux 容器，需要一层 Linux 内核。WSL2 就是微软提供的这层「真 Linux 虚拟机」，
比老的 Hyper-V 方案轻、启动快、文件互访方便。所以 Docker Desktop 会自动把引擎放到 WSL2 里，
你在 WSL 终端里敲 `docker` 就是在跟那个引擎说话。

## 2. 装 Docker（你是从零开始，这一节最费时间）

### 2.1 先确认你的 WSL 是 2 不是 1

在 **Windows PowerShell** 里执行：

```powershell
wsl -l -v
```

看 `VERSION` 那列。如果是 `1`，先升级（升级前**先把重要文件备份出来**）：

```powershell
wsl --set-version <发行版名字> 2
wsl --set-default-version 2
```

如果 `wsl -l -v` 报错或列表为空，先 `wsl --install`（它会装好 WSL2 + 一个 Ubuntu）。

### 2.2 两条安装路线怎么选

| | **A. Docker Desktop + WSL 集成** | **B. 在 WSL 里装 Docker Engine** |
|---|---|---|
| 上手难度 | 低（有图形界面） | 中（要敲一堆 apt 命令） |
| 开机自启 | 自动 | 要 `systemctl enable docker` |
| 磁盘占用 | 大（约 2~3 GB） | 小（几十 MB） |
| 免 sudo | 默认可以 | 要手动加 docker 组 |
| 常见卡点 | **忘了开 WSL Integration → WSL 里根本没有 `docker` 命令** | systemd 没开 → `systemctl` 报错 |
| **建议** | ✅ **初学者选这个** | 想把 Linux 一起学透再选 |

下面的步骤按你选的路线读，**不要两条都做**。

### 2.3 路线 A：Docker Desktop（推荐）

1. 到官网下载 **Docker Desktop for Windows**（`.exe`），双击安装
2. 安装向导里勾选 **"Use WSL 2 instead of Hyper-V"**
3. 安装完启动 Docker Desktop，等左下角小鲸鱼图标变成**绿色/稳定**（第一次启动要几分钟）
4. **设置里两处必须开**（这是 90% 的人卡住的点）：
   - `Settings → Resources → WSL Integration` → 打开 **你的发行版** 的开关 → `Apply & Restart`
   - 老版本可能是 `Settings → General` → 勾 **Use the WSL 2 based engine**，然后才出现上面那一项
5. **关掉所有 WSL 终端窗口，重新开一个**（环境变量要重新加载）
6. 在 WSL 里验证（见 2.5）

> ⚠️ **最容易的误判**：在 **Windows PowerShell** 里敲 `docker --version` 成功，就以为装好了。
> **Windows 侧能用 ≠ WSL 里能用**，两者是两套独立入口。
> 如果你正卡在这里（WSL 里报 `docker: command not found`），**直接跳到
> [§2.6 专治这一节](#26-专治装了-docker-desktop但-wsl-里没有-docker-命令)** ——
> 那是按症状分支写的排查树，**不需要重装**。
>
> 如果你有多个发行版，注意 Integration 开关是**按发行版**勾的；装到 Ubuntu 却勾了 Debian，一样用不了。

### 2.4 路线 B：在 WSL 里装 Docker Engine

```bash
# 0) 确认发行版（下面按 Ubuntu/Debian 的 apt 写）
cat /etc/os-release

# 1) 卸掉可能存在的旧版本（报「未安装」是正常的，忽略）
sudo apt remove -y docker docker-engine docker.io containerd runc

# 2) 装基础工具并加官方 GPG key 与软件源
sudo apt update
sudo apt install -y ca-certificates curl gnupg
sudo install -m 0755 -d /etc/apt/keyrings
curl -fsSL https://download.docker.com/linux/ubuntu/gpg | sudo gpg --dearmor -o /etc/apt/keyrings/docker.gpg
sudo chmod a+r /etc/apt/keyrings/docker.gpg
echo "deb [arch=$(dpkg --print-architecture) signed-by=/etc/apt/keyrings/docker.gpg] https://download.docker.com/linux/ubuntu $(. /etc/os-release && echo $VERSION_CODENAME) stable" | sudo tee /etc/apt/sources.list.d/docker.list > /dev/null

# 3) 安装（注意带 docker-compose-plugin，这样才有 `docker compose` 子命令）
sudo apt update
sudo apt install -y docker-ce docker-ce-cli containerd.io docker-buildx-plugin docker-compose-plugin

# 4) 确认 systemd 可用（WSL 里 systemd 默认可能是关的）
systemctl --version          # 报 "System has not been booted with systemd" 就先把它打开
#    打开方式：在 WSL 里编辑 /etc/wsl.conf 写入 [boot] / systemd=true 两行，
#    然后在 Windows PowerShell 里 `wsl --shutdown`，再重开终端

# 5) 启动服务并设为开机自启
sudo systemctl enable --now docker

# 6) 免 sudo（可选但强烈建议）
sudo usermod -aG docker $USER
#    ⚠️ 必须「关掉终端重开」或 newgrp docker 才生效
```

### 2.5 装完必须通过的 5 条自查（缺一条后面必卡）

```bash
docker --version                       # 1. 有版本号
docker compose version                 # 2. 注意是 compose 子命令，不是连字符的 docker-compose
docker run --rm hello-world            # 3. 能拉镜像并跑起来 → 这是最终判据
docker run --rm alpine sh -c 'echo ok' # 4. 能自定义命令
docker info | grep -E 'Server Version|Storage Driver'   # 5. 能连上引擎
```

| 报错 | 原因 | 处置 |
|---|---|---|
| `docker: command not found` | 路线 A 忘了开 WSL Integration；或路线 B 装完没重开终端 | **先看专节 [2.6](#26-专治装了-docker-desktop但-wsl-里没有-docker-命令)** / `newgrp docker` |
| `Cannot connect to the Docker daemon` | 引擎没起来；或 CLI 有了但没连上引擎 | 路线 A 看鲸鱼图标；路线 B `sudo systemctl start docker`。另见 [2.6](#26-专治装了-docker-desktop但-wsl-里没有-docker-命令) 第 3 类 |
| `permission denied ... docker.sock` | 没加 docker 组 / 没重开终端 | `sudo usermod -aG docker $USER` 后重开终端 |
| `docker compose` 提示未知命令 | 只装了旧的 `docker-compose`（v1） | 装 `docker-compose-plugin`，或临时用 `docker-compose`（**本文所有命令都写成 `docker compose`**） |
| 拉镜像一直卡住 | 网络问题 | 配镜像加速器（Docker Desktop: Settings → Docker Engine 里加 `registry-mirrors`） |

### 2.6 专治「装了 Docker Desktop，但 WSL 里没有 `docker` 命令」

**这是最常见的第一个卡点**（不是装错了，Docker Desktop 默认只服务 Windows 侧）。

**先认清一件事**：

```
Windows PowerShell 里 docker 能用  ≠  WSL 里 docker 能用
两者是两套独立入口，要分别打通
```

很多人是在 PowerShell 里敲 `docker --version` 成功就以为装好了，切到 WSL 才发现没有 —— 这时**不需要重装**，
只需要把「WSL 集成」这个开关打开。

#### 第 1 步：打开 WSL Integration（90% 的情况到这一步就解决了）

1. **确认 Docker Desktop 正在运行**：托盘/任务栏的小鲸鱼图标是**稳定（非黄色转动）**状态。
   黄色 = 还在启动，此时设置可能不可用。
2. 打开 Docker Desktop → **Settings**（右上角齿轮）
3. 左侧找到 **Resources → WSL Integration**
   - 新版（4.30+）路径就是 `Settings → Resources → WSL Integration`
   - 老版可能是 `Settings → General → 勾选 Use the WSL 2 based engine`，**然后**才出现 WSL Integration 项
4. 在 `WSL Integration` 页面里：
   - 顶部 **"Enable integration with my default WSL distro"** 打开
   - 下方列表里找到**你实际在用的那个发行版**，把它右侧的开关也打开
     （顶部那个只管默认发行版；你如果用的是非默认发行版，必须在列表里单独勾）
5. 点 **Apply & Restart**，等 Docker Desktop 重新就绪
6. **关掉所有 WSL 窗口，重新开一个**（PATH 要重新加载；不重开终端不算生效）
7. 在 WSL 里验证：

```bash
which docker                # 期望输出 /usr/bin/docker
docker --version
docker compose version
docker run --rm hello-world # 最终判据
```

#### 第 2 步：如果列表里**没有**你的发行版

按下表对号入座：

| 症状 | 原因 | 处置 |
|---|---|---|
| 列表是空的，或只有不认识的名字 | 你的发行版是 **WSL 1** —— **WSL1 发行版不会出现在这个列表里** | 在 **PowerShell** 里 `wsl -l -v` 看 `VERSION`；是 `1` 就升级：`wsl --set-version <发行版名> 2`（**升级前备份重要文件**），然后再回头看列表 |
| 发行版是**装完 Docker Desktop 之后**才装的 | Docker Desktop 没有再扫过一遍 | 托盘右键 **Quit Docker Desktop** → 重新启动；或在 PowerShell 里 `wsl --shutdown` 后再启动 Docker Desktop |
| 列表里有，开关也开了，WSL 里还是没有 | 没 Restart / 没重开终端 | 先 `Apply & Restart`，PowerShell 里 `wsl --shutdown`，再重开 WSL 终端 |
| 列表里只有别的发行版 | 你实际用的是另一个 | 勾对那个；或 `wsl -s <发行版名>` 把它设成默认，再重开 Docker Desktop |
| 找不到 Integration 这一项 | Docker Desktop 版本太旧或没装成 WSL2 后端 | 升级 Docker Desktop；并确认 `Settings → General` 里 **Use the WSL 2 based engine** 已勾 |

#### 第 3 步：`docker` 命令有了，但连不上引擎

症状是 `which docker` 有输出，但执行时报 `Cannot connect to the Docker daemon at unix:///var/run/docker.sock`。

```bash
ls -l /var/run/docker.sock     # 存在吗？
docker context ls              # 当前用的是哪个 context（应为 desktop-linux）
```

| 情况 | 处置 |
|---|---|
| `/var/run/docker.sock` 不存在 | Docker Desktop 没在运行，或 WSL Integration 实际没生效 —— 回到第 1 步 |
| 存在但 permission denied | 见 §2.5 的 docker 组那条（Docker Desktop 场景通常不需要，但重启终端后仍报错就加组） |
| `docker context ls` 里当前 context 不是 `desktop-linux` | `docker context use desktop-linux` |

#### 第 4 步：还是不行 → 干脆不用 Docker Desktop 的注入

直接在 WSL 里装一套自己的 Docker Engine（**路线 B**，见 [§2.4](#24-路线-b在-wsl-里装-docker-engine)）。
两者互不冲突，装完 WSL 里就有独立的引擎与 CLI，不再依赖 Docker Desktop 的 WSL Integration 开关。

> ⚠️ 别用「在 WSL 里 `export DOCKER_HOST=tcp://...` 去连 Docker Desktop 引擎」这条野路子 ——
> 初学者最容易在这里踩 TLS / 端口 / 重启失效的坑，收益还不如直接装 Engine。

> 💡 **判断自己到底属于哪一种**：在 WSL 里执行 `which docker` 与 `ls -l /var/run/docker.sock`，
> 两条命令的输出就能定位到上面四步里的哪一步。**把这两条的输出发我，我直接告诉你卡在哪。**

## 4. 步骤 0（已完成 ✅）：把上传目录改成可覆盖

> **状态（2026-09-24 21:30）**：这一步**已经改好了**，你不用再动手。
> 原内容是写死的 Windows 绝对路径，容器里不存在 `D:` 盘，会导致启动即失败或上传目录落错位置。
> 现值（`wayfare-backend/src/main/resources/application.yml`）：
>
> ```yaml
> file:
>   upload:
>     upload-dir: ${FILE_UPLOAD_DIR:D:/Code/Vibe coding test/Wayfare/wayfare-backend/uploads}
> ```
>
> 本机直跑不设 `FILE_UPLOAD_DIR` → 落到默认值，**行为与改动前完全一致**；容器里由 `docker-compose` 注入 `/app/uploads`。
> 你写 `docker-compose.yml` 时记住要用 **`FILE_UPLOAD_DIR`** 这个变量名（§7.5 已列出）。

**为什么要带 `:默认值`**：这样本机直跑（路线 B）**行为完全不变**，只有容器里设了 `FILE_UPLOAD_DIR` 才生效。

> 配置绑定是 `@ConfigurationProperties(prefix = "file.upload")` + 字段 `uploadDir`，
> 所以环境变量名还有一种写法是 **`FILE_UPLOAD_UPLOADDIR`**（Spring 宽松绑定：点变下划线、去掉连字符、全大写）。
> `${FILE_UPLOAD_DIR:...}` 用的则是**你自己起的占位符名**。两种写法都对，**选一种并保持一致**即可。
> 本文后面统一按 **`FILE_UPLOAD_DIR`**（配合上面这行 yml）来写。

## 5. 你写第 1 个文件：后端 `Dockerfile`

### 5.1 先想清楚 4 个问题（想不清就别写）

| 问题 | 答案 |
|---|---|
| 为什么要多阶段？ | 编译需要 JDK + Maven + **整个 src**；运行只需要 JRE + **一个 jar**。单阶段镜像会把编译工具链全带上（约 1.2 GB → 多阶段约 300 MB） |
| 为什么先 `COPY pom.xml` 再 `COPY src`？ | Docker 按「层」缓存。pom 没变就复用缓存、**不重新下载依赖**（本项目依赖首次下载要几分钟，每次都重来会疯） |
| 为什么要非 root 用户？ | ① 降低逃逸风险；② **更实际的原因**：root 写出来的上传文件属主是 root，你在 WSL 里改不动/删不掉 |
| `HEALTHCHECK` 有什么用？ | compose 的 `depends_on: condition: service_healthy` 靠它判断「后端真的能服务了」。没有它就只能靠端口探测，而 Spring 端口通了但可能还在初始化 |

### 5.2 指令逐个解释

| 指令 | 作用 | 你要注意的 |
|---|---|---|
| `FROM ... AS builder` | 定义构建阶段并命名 | 名字随你起，后面 `COPY --from=` 要对应 |
| `WORKDIR /app` | 设工作目录（不存在会创建） | 后续相对路径都基于它 |
| `COPY pom.xml .` | 只拷 pom | 放在 `COPY src` **之前**，才能利用缓存 |
| `RUN mvn ... dependency:go-offline` | 预下载依赖 | 可选优化；不做也行（编译时一并下载） |
| `COPY src ./src` | 拷源码 | 有 `.dockerignore` 才不会把 `target/` 也拷进来 |
| `RUN mvn -B -DskipTests package` | 打包 | **必须 `-DskipTests`**，理由见 5.3 |
| `FROM ... AS runtime` | 第二个阶段，干净底座 | 用 **JRE** 不是 JDK |
| `COPY --from=builder /app/target/xxx.jar app.jar` | 跨阶段拿产物 | 路径要对得上 |
| `ENV` | 设环境变量 | 可用 `JAVA_OPTS` 之类，但要和 `ENTRYPOINT` 配合 |
| `EXPOSE 8080` | **仅文档性质**，不真的开放端口 | 真正映射端口在 compose 里写 |
| `USER xxx` | 切非 root | 要在 `COPY` **之后**，并确认 jar 可读、上传目录可写 |
| `ENTRYPOINT ["java","-jar","app.jar"]` | 启动 | **用 exec 数组形式**，别用 shell 形式 |
| `HEALTHCHECK ...` | 健康检查 | 见 5.4 第 1 条 |

### 5.3 本项目的具体真值（写的时候直接用，不用猜）

| 项 | 值 |
|---|---|
| 构建基础镜像 | `maven:3.9-eclipse-temurin-17` |
| 运行基础镜像 | `eclipse-temurin:17-jre` |
| 打包命令 | `mvn -B -DskipTests package` |
| **为什么必须跳过测试** | `mvn test` 要连 **MySQL 与 Redis**，还要清日志表；构建阶段没有这些服务，必然失败 |
| 产物 jar 名 | `target/wayfare-backend-1.0.0.jar`（artifactId `wayfare-backend` + version `1.0.0`，pom 没改 `finalName`） |
| 监听端口 | **8080** |
| 健康检查路径 | **`/api/health`** ← ⚠️ **必须带 `/api` 前缀**（`server.servlet.context-path=/api`），写 `/health` 永远不健康 |
| 健康检查期望响应 | `{"status":"UP",...}` |

> 不确定 jar 名？**在写 Dockerfile 之前先在本机跑一次** `mvn -DskipTests package`，

### 5.4 最容易写错的 3 处（给思路，不给成品）

**① `HEALTHCHECK` 里用什么发请求？**
`eclipse-temurin:17-jre` 是很精简的镜像，**通常没有 `curl` 也没有 `wget`**。三种办法，各有代价：

- 自己 `apt-get install curl` → 简单，但镜像变大（几十 MB）
- 用基础镜像里可能已有的 `wget` → 先在容器里 `which wget` 确认，别凭印象写
- 用 JDK 自带工具或一行 java 发 HTTP → 不增体积，但命令很长很难看

> **建议**：先图省事装 `curl`，跑通之后想优化再换。
> 另一个常见错误：`HEALTHCHECK` 命令**只在容器内执行**，所以写 `http://localhost:8080/api/health`（容器内自己）是对的。

**② 怎么把 jar 从构建阶段搬到运行阶段？**
`COPY --from=<阶段名> <阶段内的路径> <运行阶段的目标路径>` ——
注意「阶段内的路径」是相对该阶段 `WORKDIR` 的，而两个阶段的 `WORKDIR` 可能不同。

**③ `ENTRYPOINT` 的两种写法差别很大**

```
ENTRYPOINT ["java","-jar","app.jar"]     ← exec 形式（推荐）
ENTRYPOINT java -jar app.jar             ← shell 形式（不推荐）
```

shell 形式会套一层 `/bin/sh -c`，导致 **JVM 收不到 `SIGTERM`** —— 后果是 `docker compose stop`
要干等 10 秒才强杀，后端拿不到优雅关闭的机会（连接不释放、SSE 通道不清理）。

## 6. 你写第 2、3 个文件：前端 `Dockerfile` + `nginx.conf`

### 6.1 为什么前端也要多阶段

`node:20-alpine` 里装着 Node + npm（几百 MB），但**构建完就完全没用了** ——
产物只是 `dist/` 里的一堆 `.html / .js / .css`。所以第二个阶段换 `nginx:alpine`（约 50 MB）只负责「把静态文件发出去」。

### 6.2 `npm ci` 还是 `npm install`？

本项目**有 `package-lock.json`（76 KB）** → **用 `npm ci`**。理由：

- `npm ci` 严格按 lock 文件装，**版本完全可复现**；`npm install` 可能顺手升级到新的小版本
- `npm ci` 更快，且会在 lock 与 package.json 不一致时**直接报错**（早暴露比晚暴露好）
- `npm ci` 会先删掉 `node_modules`，所以容器里不需要预置任何依赖

> ⚠️ 用 `npm ci` 时 `package-lock.json` **必须一起 COPY 进去**，否则它找不到 lock 直接失败。

### 6.3 `nginx.conf` 必须满足的 7 条（**逐条自查，这是全文最重要的一节**）

| # | 要求 | 不写会怎样 |
|---|---|---|
| 1 | `try_files $uri $uri/ /index.html;` | Vue 是 history 路由，**直接刷新 `/plan` 会 404** |
| 2 | `location /api/ { proxy_pass http://backend:8080; }` | 前端所有接口挂掉。**注意不要 rewrite 掉 `/api`** —— 后端 context-path 就是 `/api`，rewrite 掉就变 404 |
| 3 | `location /uploads/ { proxy_pass http://backend:8080/api/uploads/; }` | **图片全裂**。这是最容易被忽略的一条：后端在 context-path 内映射 `/uploads/**`，所以真实地址是 **`/api/uploads/**`**（本机开发时 Vite 代理干的就是这件事，见 `vite.config.js`） |
| 4 | 🔴 **SSE 必须关缓冲**：`proxy_buffering off;`（配合 `proxy_cache off;` 与响应头 `X-Accel-Buffering: no`） | nginx 默认会把响应攒起来再发。**AI 生成行程会「一直转圈」**，骨架和文案都出不来，最后超时 |
| 5 | 🔴 **SSE 要加长超时**：`proxy_read_timeout` **必须大于后端 `trip.sse-timeout-ms`（默认 600000 ms = 10 分钟）**，建议 900s 或 1800s | nginx **默认 60 秒**就断。表现是生成到一半突然失败（实测一次生成 87.7 秒，必被掐断） |
| 6 | `client_max_body_size 20m;` | 上传图片报 **413**；后端限制是 10 MB/文件、100 MB/请求 |
| 7 | 静态资源缓存（可选）：对 `js/css/png/...` 设 `expires` | 不设也能用，只是每次刷新都重下 |

> 🔴 **第 4、5 条是本项目最容易踩的 Docker 坑**，而且**本机 `vite dev` 完全不会暴露它**
> （开发服务器不做缓冲）—— 只有上了 nginx 才第一次出现。别以为「本机好好的，容器里也应该好」。
>
> SSE 相关的推荐设置（思路，具体自己写）：
> `proxy_http_version 1.1;` + `proxy_set_header Connection '';` + `proxy_buffering off;` +
> `proxy_cache off;` + 长 `proxy_read_timeout`。
> 也可以只给 **SSE 那两个接口**单独开 `location`（`/api/trip/plan/stream` 与
> `/api/trip/<id>/regenerate-copy`），其余接口保持默认 —— 更安全，但配置更复杂。

### 6.4 前端构建期的 2 个真值

| 项 | 值 |
|---|---|
| 构建命令 | `npm run build` |
| 产物目录 | `dist/`（交给第二阶段 `COPY --from=builder ... /usr/share/nginx/html`） |

**关于前端地图 AK**：变量名是 **`VITE_BAIDU_MAP_AK`**（**不是**手册里写的 `BAIDU_MAP_JS_AK`），
且它是 **Vite 构建期变量** —— 要用就必须在 `docker build` 时以 `--build-arg` 传进去，**运行时再传没用**。

**配了也不会画出点位与连线**。所以这一项建议**先跳过**，别在这上面花时间（见 [开发文档 §19](Wayfare-开发文档.md#十九已知局限与扩展方向)）。

## 7. 你写第 4 个文件：`docker-compose.yml`

### 7.1 compose 帮你解决的 4 件事

1. **网络**：自动建一个网络，服务之间用**服务名**互访（`mysql`、`redis`、`backend`）
2. **依赖顺序**：`depends_on` 决定谁先起
3. **卷**：数据持久化
4. **变量**：从一个 `.env` 文件读变量注入到各容器

### 7.2 四个服务：你各自要决定什么

| 服务 | 要决定的事 |
|---|---|
| `mysql` | 镜像（`mysql:8.0`）、root 密码从 `.env` 取、**挂 `db/*.sql` 到 `/docker-entrypoint-initdb.d`**、数据卷、healthcheck |
| `redis` | 镜像（`redis:7-alpine`）、数据卷（可选）、healthcheck |
| `backend` | `build:` 指向 `./wayfare-backend`、**必须覆盖 4 项配置**（见 7.5）、上传目录卷、`depends_on` mysql+redis 且要 `service_healthy` |
| `frontend` | `build:` 指向 `./wayfare-frontend`、**端口映射给 Windows 用**、`depends_on` backend |

### 7.3 🔴 mysql 初始化的三个细节

**① `/docker-entrypoint-initdb.d` 只在「数据目录为空」时执行。**

第一次 `docker compose up -d` 会跑 `db/schema.sql` 与 `db/schema-trip.sql`；**第二次起就不跑了**。
你后来改了 schema、或想加个表，指望重启生效 —— **不会生效**。

要让初始化重跑，只能**删掉数据卷**（`docker compose down -v`）—— 那等于**把库清空重来**。
所以：**改 schema 要走 `docker compose exec mysql mysql ...` 手工执行 ALTER，不要指望重启。**

**② `db/schema-trip.sql` 对表是 `DROP TABLE` 后重建。**

它一执行，`sys_config`（你后台改过的厂商 / AK / 单价）、`trip` / `trip_item`（用户行程）**全部清空**。
所以：挂到 `initdb.d` **只在首次建库时**是对的（那时本来就是空库）；
**任何时候都不要在已运行的库上手工重跑这个脚本**。

**③ 挂载方式与执行顺序**

把 `db/` 里那两个 `.sql` 挂到容器里的 `/docker-entrypoint-initdb.d`。MySQL 官方镜像会按
**文件名字典序**执行该目录下的 `*.sql`。当前两个文件叫 `schema.sql` / `schema-trip.sql`，
字典序里 `schema-trip.sql` 在前、`schema.sql` 在后 —— **两者互不依赖**（各自带
`CREATE DATABASE IF NOT EXISTS` 与 `USE wayfare`），所以顺序无所谓。
但以后若加了有依赖的脚本，请重命名成 `01-xxx.sql` / `02-yyy.sql` 显式控制顺序。

> ⚠️ 别把整个仓库目录挂进 `initdb.d` —— 那里面不是 `.sql` 的文件会被一起处理/报错，而且构建上下文也会变脏。
> 只挂那两个文件（或只挂 `db/` 目录，但要确认里面只有 `.sql`）。

### 7.4 🔴 `depends_on` ≠ 「等它准备好」

```yaml
# ❌ 这只能保证「先启动 mysql 容器」，不保证 MySQL 已经能接受连接
depends_on:
  - mysql

# ✅ 这才是「等健康」
depends_on:
  mysql:
    condition: service_healthy
```

配合给 `mysql` / `redis` 写 `healthcheck`（MySQL 常用 `mysqladmin ping`；Redis 常用 `redis-cli ping`）。
不写这个，经典症状是：**后端启动时报「连接数据库失败」，但 `docker compose ps` 显示四个容器都 Up**。

### 7.5 容器里必须覆盖的 4 项（真值表）

| 配置 | 本机值（`application.yml`） | 容器里必须改成 | 怎么改 |
|---|---|---|---|
| 数据库地址 | `jdbc:mysql://**localhost**:3306/wayfare?...` | host 换 **`mysql`** | 环境变量 `SPRING_DATASOURCE_URL` |
| Redis 地址 | `spring.data.redis.host: **localhost**` | 换 **`redis`** | 环境变量 `SPRING_DATA_REDIS_HOST` |
| 上传目录 | `D:/Code/Vibe coding test/Wayfare/wayfare-backend/uploads` | `/app/uploads`（或你选的路径） | 环境变量 `FILE_UPLOAD_DIR`（**依赖第 4 节的 yml 改动**） |
| 数据库密码 | 本机 `123456` | `.env` 里的强密码 | `MYSQL_ROOT_PASSWORD` **和**后端连库用的密码**必须是同一个值** |

> 🔴 **最后一行是最容易错的**：MySQL 容器的 root 密码、和后端连库的密码，**是两处独立配置，必须写同一个值**。
> 只改一处 → 后端反复重连失败。
>
> 关于「后端容器能不能用 root 连」：MySQL 官方镜像默认把 root 建成**可从任意主机连**
> （可用 `MYSQL_ROOT_HOST` 收紧）。这既是初学者省事的原因，**也是必须配合 7.6 的原因**。
> 起来后建议自己核一遍：
> ```bash
> docker compose exec mysql mysql -uroot -p"$MYSQL_ROOT_PASSWORD" -e "SELECT user, host FROM mysql.user;"
> ```
> 看到 `root | %` 就是「允许从任意主机连」。
> **生产环境请建一个专用业务用户**，别用 root。

### 7.6 端口映射：哪些该给 Windows 用

| 服务 | 建议 | 理由 |
|---|---|---|
| `frontend` 容器 80 | ✅ 映射，例如 `8080:80` | 你要用浏览器访问 |
| `backend` 容器 8080 | ⚠️ 可选，例如 `8081:8080` | 只在你想直接打接口 / 看 Swagger 时开。走前端反代的话**不必开** |
| `mysql` 容器 3306 | ❌ **建议不映射** | 初学者最常见的「把数据库裸露到局域网/公网」事故。真要用 Navicat 连，再开，且**只绑 `127.0.0.1:3306:3306`** |
| `redis` 容器 6379 | ❌ **建议不映射** | 同上，且 Redis 默认**无密码** |

> 判据：**只有「你本人要用 Windows 上的程序主动去连」的端口才需要映射**。
> 容器之间互访靠服务名，不经过宿主机端口。
>
> ⚠️ **本机已经有 MySQL80 服务占着 3306**（实测 `netstat` 可见 `0.0.0.0:3306 LISTENING`）。
> 所以**就算你想映射 `3306:3306` 也会直接失败**（端口冲突，容器起不来）。
> 真要在宿主上连容器的库，请映射到别的端口，例如 `127.0.0.1:3307:3306`。
> 同理 Redis 的 6379 也有一个已有实例在跑（本项目本机开发用的那个）。

### 8.1 应该包含的键

| 变量 | 必填 | 说明 |

| `MYSQL_ROOT_PASSWORD` | ✅ | 数据库密码；**MySQL 容器与后端两处共用** |
| `MYSQL_DATABASE` | ⬜ | 设为 `wayfare`（脚本里也会建，显式写更清楚） |

| `GLM_API_KEY` | ⬜ | 同上 |
| `DEEPSEEK_API_KEY` | ⬜ | 同上 |
| `BAIDU_MAP_AK` | ⬜ | 不填则地图整体不可用，全流程走估算（`ESTIMATED`） |
| `JWT_SECRET` | ⬜（生产 ✅） | 不填则用 yml 里的开发默认值，**生产必须改**（HS256 要求 ≥32 字节） |

### 8.2 🔴 `LLM_ACTIVE_PROVIDER` 会被数据库静默覆盖（本项目特有的坑）

本项目的配置是**三层**：

```
L1 启动层   application.yml（环境变量可以覆盖它）
L2 运行层   sys_config 表 + Redis 缓存 30s   ← 优先级更高
L3 降级层   熔断器 + 分级 Provider
```

**读取优先级是「L2 覆盖 L1」**。而 `sys_config` 的内容是 MySQL **首次初始化时**
由 `db/schema-trip.sql` 的 `INSERT` 写进去的，初始值是：

| 键 | 脚本初始值 |
|---|---|
| `llm.active-provider` | **`qwen`** |
| `llm.fallback-order` | `qwen,glm,deepseek` |
| `map.enabled` | **`false`** |

所以：**你在 `.env` 里写 `LLM_ACTIVE_PROVIDER=glm`，会被库里的 `qwen` 盖掉，而且不会有任何报错。**

**两条正确做法**（选一条）：

1. **起完去后台改**（推荐，顺便验证热生效）：登录 → `/admin/connectors` → 切厂商 / 开地图。
   改完 **≤30 秒**生效（`sys:config` 缓存 TTL），**不用重启容器**。
2. **首次初始化前改脚本**：把 `db/schema-trip.sql` 里那两条 `INSERT` 的初始值改成你要的，
   再让 MySQL 首次初始化。⚠️ 只对**空库**有效（见 7.3）。

> 同理，`map.enabled` 初始是 `false` —— **想开地图也得去后台改**（或改 INSERT）。
> 好消息是：**初始就关着地图，正好能让首次部署「零外部依赖、零配额消耗」地跑通。**

### 8.3 前端 `VITE_BAIDU_MAP_AK` 是构建期变量

- 变量真名是 **`VITE_BAIDU_MAP_AK`**（手册里写的 `BAIDU_MAP_JS_AK` 在本项目里不存在）
- Vite 的 `import.meta.env.*` 在 **`npm run build` 时就被内联进 JS** 了，
  放 `.env` 里运行时注入**完全没用**，必须 `docker build --build-arg` 传
- **但本项目未接入百度地图 JS API**，配了也不会画地图 → **建议先跳过**

## 10. 日常运维（初学者版）

### 10.1 看日志的 3 种姿势

```bash
docker compose logs -f backend          # 跟某个服务的实时日志（最常用）
docker compose logs --tail=100 backend  # 只看最后 100 行
docker compose logs backend | grep -i error
```

> 后端日志里**有中文**。WSL 终端一般是 UTF-8，正常显示；
> 如果换到 Windows PowerShell 里执行可能要 `chcp 65001` 才不乱码 ——
> **这也是建议一切命令都在 WSL 里跑的原因之一**。

### 10.2 `stop` / `restart` / `down` / `up --build` 的区别

| 命令 | 效果 | 数据 | 什么时候用 |
|---|---|---|---|
| `docker compose stop` | 停容器，**不删** | 保留 | 临时停一下 |
| `docker compose start` | 启动已存在的容器 | 保留 | 停完再开 |
| `docker compose restart backend` | 重启某个服务 | 保留 | 改了 `.env`、想重读环境变量 |
| `docker compose down` | 停并**删除**容器与网络 | **卷保留** | 想重建容器 |
| `docker compose down -v` | 连**卷一起删** | 🔴 **全丢** | 只在「就是要清空重来」时用 |
| `docker compose up -d --build` | 重新构建镜像并起 | 保留 | 改了代码 / Dockerfile |

### 10.3 备份与恢复

```bash
# 备份（把库导成文件，落在当前目录）
docker compose exec -T mysql mysqldump -uroot -p"$MYSQL_ROOT_PASSWORD" --databases wayfare \
  > backup_wayfare_$(date +%Y%m%d_%H%M).sql

# 恢复（注意：会覆盖同名库里的数据）
docker compose exec -T mysql mysql -uroot -p"$MYSQL_ROOT_PASSWORD" < backup_wayfare_20260924_1900.sql
```

> **升级前、`down -v` 前、动 schema 前，先备份。** 三条都要。
> 上传的图片在 volume 里，**数据库备份不含它** —— 想连图一起备，要单独处理卷目录。

### 10.4 升级流程（改了代码怎么重新部署）

> 💡 **日常改 bug 请先看 [§10.6](#106-本地直跑与容器怎么共存以后改-bug-就这么走)** ——
> 那里讲了「改哪类文件要重建哪个服务」的对照表，以及为什么 `restart` 不够。本节是它的简版。

```bash
git pull                                   # 或你自己改完代码
docker compose up -d --build               # 重建并起（数据保留）
docker compose ps                          # 确认健康
```

| 改了什么 | 需要做什么 | 会不会丢数据 |
|---|---|---|
| 后端 Java 代码 | `up -d --build`（可只重建 backend） | 不会 |
| 前端页面 | `up -d --build` | 不会 |
| `db/schema*.sql` | 🔴 脚本只在空库执行 → **手工 ALTER**，或 `down -v` 清空重来 | 手工 ALTER 不会；`down -v` 会 |
| `.env` | `docker compose up -d`（让 compose 重读） | 不会 |
| `application.yml` | 重新 build backend | 不会 |

### 10.5 磁盘清理

```bash
docker system df                   # 先看占用
docker system prune                # 删「没被使用」的镜像/容器/网络（不会删卷）
docker system prune -a --volumes   # 🔴 连卷一起删 —— 会清掉数据库！
```

> 🔴 **`--volumes` 不要随手加**。这是新手最常见的「手滑清库」操作。

### 10.6 本地直跑与容器怎么共存（**以后改 bug 就这么走**）

#### 先纠正一个几乎人人都有的预期：改代码，容器**不会**自动更新

容器里跑的是**构建时打进镜像的产物**（后端是 jar、前端是 dist），相当于一张**快照**。
本地改文件**不影响**正在运行的容器 —— 必须重新构建。

| 改了什么 | 要做什么 | 大约多久 |
|---|---|---|
| 后端 `.java` | 重新 build backend → `docker compose up -d --build backend` | 约 1 分钟 |
| 后端 `resources/application.yml` | **也要重新 build** —— 它被打进 jar 了，**`restart` 不够** | 约 1 分钟 |
| 前端 `src/**` | `docker compose up -d --build frontend` | 20~30 秒 |
| 根目录 `.env` | 不用 build，但要 **`docker compose up -d`**（重建容器） | 几秒 |
| `db/*.sql` | 🔴 只在**空库**时执行过一次 → 改了要手工 `ALTER`，或 `down -v` 清库重来 | — |
| 后台改的 `sys_config` | 在 MySQL 的 volume 里，**重建容器不丢** | — |

> ⚠️ **最容易错的是第 1、2 条**：很多人以为 `docker compose restart backend` 就能让新代码生效 —— **不能**。
> `restart` 只是把**原来那个容器**重启一遍，里面还是旧镜像。
>
> ⚠️ 还有一个隐形坑：**`.env` 改动后 `restart` 也不会生效**。
> 环境变量是**创建容器时**注入的、之后固定不变 → 必须 `up -d`（它会按需重建容器）。

#### 推荐的分工：两套环境，各干各的

| | **本机直跑（路线 B）** | **容器（路线 A）** |
|---|---|---|
| 用途 | **日常改 bug / 调试** | 演示、交付、换机器一键起 |
| 改完怎么生效 | 后端重启（几秒）、前端 HMR（秒级） | `docker compose up -d --build` |
| 数据库 | 本机 MySQL80（`localhost:3306`） | 容器里**另一个** MySQL（数据在 volume） |
| 上传文件 | `wayfare-backend/uploads/` | 容器 volume |

**所以改 bug 用本机直跑，改完再重建容器去验证/演示。** 这是最省心的组合。

#### 🔴 但要知道：这两套环境默认是**两套独立的数据**

- 本机直跑连的是 **本机 MySQL80（3306）**；容器里有**另一个 MySQL 实例**，数据存在它自己的 volume 里。
- 两边表结构相同，但**内容互不相通** —— 本机生成的行程，容器里看不到；反之亦然。
- 本机库里现有真实数据：`trip` **2** 条、`user_travel_profile` **2** 条、`poi_cache` **197** 条、
  `sys_config` **19** 条（比脚本的 23 条少 4 条，就是 §11.5 说的那 4 个后加的键）。
  而容器首次初始化用的是 `db/*.sql` 的**种子数据**（只有 admin + 8 个分类）。

三种处理方式，按需选：

| 方案 | 怎么做 | 代价 |
|---|---|---|
| **① 维持两套**（默认，最省事） | 什么都不用做 | 容器里没有你的历史数据，演示时是「干净系统」 |
| ② 让本机直跑连容器的库 | 容器 mysql 映射成 `127.0.0.1:3307:3306`
（**不能映射 3306 —— 本机 MySQL80 已经占着它**），再在 WSL 里
`export SPRING_DATASOURCE_URL="jdbc:mysql://localhost:3307/wayfare?useUnicode=true&characterEncoding=utf8&useSSL=false&serverTimezone=Asia/Shanghai&allowPublicKeyRetrieval=true"` 后启动本机后端 | 每次启动都要带这个环境变量；两边写入互相影响，容易搞混 |
| ③ 干脆只用一套（本机直跑也连容器库） | 先按 §10.3 备份本机库 → 停掉本机 MySQL80 服务 → 容器 mysql 映射 `127.0.0.1:3306:3306` → 把备份导进容器。这样本机直跑的 `localhost:3306` 就直接是容器库 | 本机 MySQL80 停用；**务必先备份与导入，否则「数据不见了」** |

> **建议：先按 ① 走通，别在这上面纠结。** 等容器跑顺了、真的需要「演示时带上历史数据」，
> 再按 ③ 做一次（那时你已经熟悉 docker compose 了）。

#### 「重建」不贵 —— 别为此去折腾热更新

Docker 的分层缓存让重建很快：只改后端约 1 分钟、只改前端 20~30 秒，
mysql / redis **不受影响**（`up -d --build` 只重建变了的服务，也可以只写 `... --build backend`）。

> ❌ **不建议**为了「改完自动生效」在容器里搞热更新（后端 bind mount `src` + devtools、
> 前端在容器里跑 `vite dev`）。那会引入一串新问题：`node_modules` 要不要挂卷、dev server 的
> host/端口配置、WSL 挂载下的文件监听性能……
> **本机直跑本来就是干这个的** —— 让它干。

## 11. 故障排查表

### 11.1 装 Docker 阶段

| 现象 | 根因 | 处置 |
|---|---|---|
| WSL 里 `docker: command not found` | Docker Desktop 没开 WSL Integration；或装完没重开终端 | 见 §2.3 第 4 步 |
| `Cannot connect to the Docker daemon` | 引擎未启动 | Docker Desktop 看图标；Engine 路线 `sudo systemctl start docker` |
| `permission denied /var/run/docker.sock` | 不在 docker 组 | `sudo usermod -aG docker $USER` → **重开终端** |
| `docker compose` 是未知命令 | 只有 v1 的 `docker-compose` | 装 `docker-compose-plugin` |
| `systemctl` 报 "System has not been booted with systemd" | WSL 没开 systemd | 写 `/etc/wsl.conf` 的两行（`[boot]` / `systemd=true`）→ `wsl --shutdown` → 重开 |

### 11.2 构建阶段

| 现象 | 根因 | 处置 |
|---|---|---|
| `docker build` 卡在拉镜像/依赖很久 | 首次下载 + 网络 | 配镜像加速器；耐心等一次，之后有分层缓存 |
| 依赖每次都重新下载 | `COPY pom.xml` 写在了 `COPY src` **之后** | 调整顺序（见 §5.1） |
| 构建上下文几个 GB、非常慢 | 没写 `.dockerignore` | 排除 `target/`、`node_modules/`、`uploads/` |
| Maven 报找不到依赖 | 代理 / 私有仓库 | 在 Dockerfile 里配 `settings.xml`，或构建时用 `--network host` |
| `npm ci` 报 lock 与 package.json 不一致 | **只 COPY 了 package.json 没 COPY `package-lock.json`** | 两个一起 COPY |
| `npm ci` 报 Node 版本不符 | 基础镜像 Node < 18 | 用 `node:20-alpine` |
| 前端构建 OOM / 卡死 | 内存不足 | 给 Docker Desktop 多分内存；或 `NODE_OPTIONS=--max-old-space-size=2048` |
| 容器起来报「找不到 jar」 | 产物名写错 | `ls target/*.jar` 核对真实名字（§5.3） |

### 11.3 启动与网络阶段

| 现象 | 根因 | 处置 |
|---|---|---|
| 四个容器都 Up，但后端连不上数据库 | `depends_on` 没等健康；或 `SPRING_DATASOURCE_URL` 还写着 `localhost` | §7.4 + §7.5 |
| 后端反复重连数据库、日志一堆 `Access denied` | **两处密码不一致**（MySQL 容器 vs 后端连库） | 用同一个 `.env` 变量值（§7.5） |
| 前端打开是 nginx 默认欢迎页 | `nginx.conf` 没挂到 `/etc/nginx/conf.d/default.conf`，或没覆盖掉默认配置 | 检查 COPY 目标路径 |
| 前端刷新 `/plan` 变 404 | nginx 缺 `try_files ... /index.html` | §6.3 第 1 条 |
| 页面能开但所有接口 502 | `/api` 反代指向错，或把 `/api` rewrite 掉了 | §6.3 第 2 条 |
| **图片全是裂的** | 漏了 `/uploads` → `/api/uploads` 这条反代 | §6.3 第 3 条（**本项目高频坑**） |
| **生成行程一直转圈、最后超时** | nginx 缓冲了 SSE；或 `proxy_read_timeout` 默认 60s 掐断 | §6.3 第 4、5 条（**本项目最高频坑**） |
| 上传图片报 413 | `client_max_body_size` 太小 | 设 `20m` |
| 容器时间不对 / 日期差 8 小时 | 时区 | 容器内设 `TZ=Asia/Shanghai` |
| 端口被占用起不来 | Windows 上有别的程序占了 8080 | 改映射的宿主端口，例如 `8088:80` |
| 改了 `.env` 没生效 | 没重启容器 | `docker compose up -d` 或 `restart <服务>` |
| 改了源码没生效 | 忘了 `--build` | `docker compose up -d --build` |

### 11.4 应用行为阶段

> 这一节的问题**与容器无关**，本机直跑（路线 B）同样会遇到，所以都保留。

| 现象 | 根因 | 处置 |
|---|---|---|
| 某厂商一直 `LLM_AUTH_FAIL` | Key 无效/过期，或模型名不对 | 后台 `/admin/connectors` 看失败原因四分类（没配 Key / 网络不通 / 认证失败 / 限流） |
| `model_not_found`，文案像没权限 | **模型 id 大小写不对**（百炼必须全小写 `qwen3.8-flash`） | 改 `application.yml` 的 `llm.providers.qwen.model` |
| 请求跑满超时、什么都拿不到 | **推理模型没下发思考强度**（GLM 5.3 / DeepSeek 都是推理模型，强制思考） | 确认 `reasoning-effort`（GLM）/ `reasoning_effort`（DeepSeek）已配；DeepSeek 写成 `effort` 会被**静默忽略** |
| 长输出阶段超时，换一家就正常 | 长输出（CANDIDATE / COMPOSE）真的需要 90 秒以上 | `llm.timeout-ms` ≥ 240000（L2 键，改完不重启即生效） |
| 连续失败后整批生成都失败 | **熔断已打开**（大模型默认 3 次失败即跳闸） | 等 300 秒半开，或调高 `llm.breaker.fail-threshold`；批量跑前先清 `cb:fail:*` |
| 成本显示「未配置」而不是数字 | 单价是 0（= 未配置），或该行 `provider=map`（地图无单价） | 填 `llm.price.{vendor}-input` / `-output`，**用字符串存小数**（INT 会把 0.3 取整成 0） |
| `COMPOSE` 阶段 `LLM_PARSE_FAIL` | `max-tokens` 太小，长 JSON 被截断 | qwen 4096 / glm 16384 / deepseek 32768 |
| 某厂商配置改了不生效 | 🔴 **L2（`sys_config`）覆盖 L1（环境变量 / yml）** | 去后台改，或改 `db/schema-trip.sql` 的 INSERT（§8.2） |
| 后台某个键找不到 | 现网库缺该键（本项目 `llm.breaker.*` / `llm.price.qwen-*` 就是这么缺的） | 手工 `INSERT`，SQL 见 §11.5 |
| 接口返回 200 但地图结果为空 / 报 `MAP_AUTH_FAIL` | **百度 AK 有误时也返回 `status=200`** | 用 `GET /api/connector/map/search` 看原始返回；重新申请**服务端**类型的 AK |
| 地图报 401 | 并发超 3 QPS，**不是日额度用完** | 降并发；项目已有请求间隔与早停 |
| 地图结果全是城市级噪声 | 用了 `tag` 参数（填错不报错） | **只用 `query`** |
| 某个县搜出来 0 条 | 县级区域覆盖不足（实测 `寿阳+古建筑` = 0、`大同+古建筑` = 14） | **做演示挑城市** |
| 明明调通了，第二次却查不到 | **空结果被缓存了 24 小时**（已知缺陷：只挡 `null` 不挡空 List） | `docker compose exec redis redis-cli --scan --pattern 'map:poi:*'` 取键后 `del`（**该缺陷未修**） |
| 熔断一直不恢复 | 300 秒 + 半开试探仍失败 | 调好后 `POST /api/connector/map/breaker/reset` 手动复位 |
| 关掉地图后行程没有距离 | **这是设计如此**：`ESTIMATED` 模式下数值列必须为 NULL | 铁律一，不是 bug（见 [开发文档 §19](Wayfare-开发文档.md#十九已知局限与扩展方向)） |
| 想验降级效果但测不出熔断 | 请求命中了 POI 缓存，根本没走到百度 | 先清 Redis 的 `map:poi:*`（演练脚本已内建这一步） |
| 前端 401 反复跳登录 | token 过期或已登出（黑名单命中） | 重新登录；Redis 不可用时黑名单会失效 |
| 生成了但地图是空的 | **项目未接入百度地图 JS API**（未实现项） | 不是配置问题（见 §6.4） |
| 删了一条行程但库里还有孤儿行 | `trip` 表**无外键** | 按序清 `trip_item` → `trip_day` → `trip` + 两张日志表 |
| 跑 `mvn test` 失败 | 库里残留了日志数据（`AiLogServiceTest` 断言**绝对条数**） | 先 `DELETE FROM ai_generation_log; DELETE FROM external_call_log;` |

| # | 手册验收项 | 你怎么自查 | 期望结果 |
|---|---|---|---|

## 附录 B：把本机数据搬进容器（可选）

容器首次初始化是**空库 + 种子数据**（admin 账号 + 8 个分类）。如果你想让容器里也有
本机的画像 / 行程 / POI 缓存，先在本机导出、再导入容器：

```bash
# 1) 本机导出（只导数据，不导结构 —— 结构由 schema 脚本建）
mysqldump -uroot -p --no-create-info --complete-insert wayfare \
  user_travel_profile trip trip_day trip_item poi_cache > local_data.sql

# 2) 拷到容器并导入（此时容器已初始化完成、22 张表就位）
docker compose cp local_data.sql mysql:/tmp/local_data.sql
docker compose exec mysql sh -c 'mysql -uroot -p"$MYSQL_ROOT_PASSWORD" -D wayfare < /tmp/local_data.sql'
```

> ⚠️ 两个注意点：
> ① **顺序必须是先容器初始化、后导入** —— 反过来会被 `schema-trip.sql` 的 `DROP TABLE` 清掉；
> ② `trip` / `trip_day` / `trip_item` 主键自增，若本机与容器的 ID 冲突会报错（干净空库一般不会）。
> 导完记得 `rm local_data.sql`（**别把它提交进仓库**）。

FILE_UPLOAD_DIR         /app/uploads        ← 依赖 application.yml 的那 1 行改动（§4）

### 关键真值

| 项 | 值 |
|---|---|
| 后端 jar | `target/wayfare-backend-1.0.0.jar` |
| 健康检查 | `GET /api/health`（**必须带 `/api`**） |
| 前端构建产物 | `dist/` |
